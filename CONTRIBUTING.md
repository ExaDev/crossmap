# Contributing

`pnpm install` sets up the git hooks (`prepare: husky`). From then on:

- **Pre-commit** lints and fixes staged TypeScript (`lint-staged`).
- **commit-msg** checks the message against [Conventional Commits](https://www.conventionalcommits.org/) with commitlint. Describe the code change in the subject, not the review that prompted it.
- **Pre-push** runs the `prepush` task (build, typecheck and tests, through turbo), so a push that CI would reject fails locally first.

## Before opening a PR

`pnpm run prepublishOnly` runs the gate CI enforces: lint, build, typecheck over both tsconfig programs, tests, `publint` and `attw --pack --profile esm-only`. The build comes before typecheck and tests because the schema generation script imports the built `dist` and the schema tests read the generated schema; `turbo.json` records that order, so running `pnpm typecheck` or `pnpm test` on a clean tree builds first. CI also packs the tarball and installs it into a clean project on each supported Node line, which is the check that the exports map works for a consumer. Tests are colocated as `*.unit.test.ts`.

## Constraints a change must preserve

- **Decode is the inverse of encode, by construction.** Each two-way operation implements both halves next to each other in `src/ops/`, and the executor swaps `from` and `to` for decode. A new operation ships with its inverse, a row in the deterministic corpus (`src/corpus.ts`) and a documented condition under which the inverse holds. A lossy operation is a one-way rule, never a two-way rule with a caveat.
- **A failure is loud.** An absent `from` path, an unmapped enum value, a split part containing its separator and a value of the wrong type all throw. The one non-throwing branch is a `when` that is false or indeterminate, which skips its rule. Do not add defaults, fallbacks or pass-through for a value the crosswalk did not describe.
- **Paths are data, not code.** A document or crosswalk must never reach `Object.prototype`. Read with own-property checks and write through `setOwn` in `src/own.ts`, never `record[key]`, and keep `__proto__` out of the path grammar in every spelling (bare and quoted). Record keys and array indices are distinct step kinds in a parsed path and in every trail, so a key spelled with digits is never treated as an index. Compare paths by their canonical spelling (`canonicalPath` in `src/paths.ts`), never by the raw string, and keep `formatPath` the exact inverse of `parsePath`.
- **One schema defines the format.** The Zod schemas in `src/crosswalk.ts` are the single definition, and the JSON Schema is generated from them. Predicates are trilean's `PredicateNodeSchema`, referenced rather than copied.
- **Task order and caching live in `turbo.json`.** Each task is an underscore-prefixed leaf script (`_build`, `_typecheck`, `_test`, `_lint`) and the public script of the same name is `turbo run _<task>`. Ordering is a `dependsOn` edge, never a sequence of commands in a hook, a workflow or a script, so every entry point (hook, CI, a developer's shell) gets the same order and the same cache. `src/turbo.unit.test.ts` fails when a script, task or hook drifts from this. Incremental state that lives outside turbo's task cache is restored by its own CI cache step: the lint scripts cache by file content (mtimes do not survive a checkout) and `tsc` writes its build info beside each tsconfig, which the CI typecheck job caches.
- **Generated files are never hand-edited.** `dist/` comes from `pnpm build` and is gitignored. `schemas/crossmap.schema.json` is committed: `cargo xtask schema`, run in `rust/`, writes it from `rust/crates/crossmap/src/schema.rs`, and `cargo test` fails when the committed file differs from what the crate generates or from the schema the TypeScript generator wrote before the port (`rust/tests/fixtures/pre-port-crossmap.schema.json`). `pnpm build` writes the same bytes from the Zod schemas. If the schema looks wrong, fix the generator, never the file.
- **No wall-clock figures in tests or docs.** Assert structure and counts of work.
- **The executor answers to a reference.** `test/support/reference-executor.ts` is the plain rule-at-a-time executor, and the property tests in `src/executor-reference.unit.test.ts` require the same output, key order included, or the same error from the shipped one over generated crosswalks and documents. A deliberate change to what encode or decode does is made in both, in the same commit; a change that only makes them faster changes the shipped one and leaves the reference alone. `pnpm bench` measures a change against a hand-written copy, as ratios and input reads per node rather than times.

## The wasm package

`packages/crossmap` is the npm package built from the Rust workspace: `rust/bindings/crossmap-wasm` (wasm-bindgen, no input or output) compiled to wasm, with the API, the error classes and the command's Node shim beside it in `rust/bindings/crossmap-wasm/js/`. `pnpm --filter ./packages/crossmap run build` runs `cargo xtask npm crossmap` through `scripts/rust.sh`, which needs the `wasm-bindgen` command at the version `rust/Cargo.lock` pins (`sh scripts/rust.sh install-wasm-bindgen`) and the JSON Schema in `schemas/`, which it copies into the package. The xtask writes `packages/crossmap/dist` and `packages/crossmap/schemas` (build output, gitignored) and fails when the manifest's `./dist/` paths and the files it wrote differ.

`pnpm --filter ./packages/crossmap run test` packs the package with `npm pack`, checks the tarball holds exactly the published files, installs it into a fresh directory and runs `packages/crossmap/test/` there in plain Node: the conformance corpus (every kind except the JSON Schema kinds), the command's end-to-end scenarios and the API's contract. `run check:package` runs `publint` and `attw --pack --profile esm-only`.

## The Rust workspace

`rust/` holds the core crate (`crates/crossmap`), the command (`crates/crossmap-cli`), the wasm binding the npm package is built from (`bindings/crossmap-wasm`), the Python binding built into the `crosswalk-codec` wheel (`bindings/crossmap-py`), the conformance runner and the xtask. `sh scripts/rust.sh <task>` runs cargo from `rust/` against the committed lock file and the pinned toolchain, and CI runs the same tasks: `fmt`, `clippy`, `test`, `conformance` (every case of the corpus, none skipped), `deny`, `schema-check`, `published-dependencies` (fails, naming it, while a path dependency of a published crate is not on crates.io), `publish-dry-run` and `packaged-schema`. `python3 -I scripts/release-version.py check` fails when the manifests disagree on the release version.

The Python package is built with `maturin build --release --locked` in `rust/bindings/crossmap-py` and tested by installing the wheel into a fresh environment with `tests/requirements.txt` (hashed, generated from `pyproject.toml`'s `test` group by the command at its head) and running `pytest` there. The same environment runs `ruff check`, `ruff format --check` and `mypy python tests`.

## Releases

A push to `main` runs the `release` job in `ci.yml` once every check has passed. semantic-release reads the conventional commits since the last tag and computes the next version, `scripts/semantic-release-version.mjs` writes it into `rust/Cargo.toml` (which every crate and, through maturin, the wheel inherit), `rust/Cargo.lock` and `packages/crossmap/package.json` and regenerates the schema whose `$id` names it, and the release commit, `CHANGELOG.md` included, is tagged and pushed with a GitHub Release. `release.config.js` holds the commit types and the release level each triggers, and commitlint imports the same list.

The tagged commit is then built again by `artefacts.yml`, the same workflow every pull request runs: the npm package, the wheels (manylinux, musllinux, macOS and Windows) and the sdist, and the crates, each tested from its installed artefact, put through `cargo publish --dry-run`, `twine check --strict` and `npm publish --dry-run`, and checked by `scripts/verify-artefacts.py` to carry the one version and the one schema. Three jobs publish exactly those artefacts: `crossmap` and `crossmap-cli` to crates.io, `crosswalk-codec` to PyPI and `crossmap` to npm, each through OIDC trusted publishing from `ci.yml` in the `release` environment, with no stored registry token. Each skips what its registry already holds, so re-running a failed release completes it.

Never hand-bump a version or edit `CHANGELOG.md`: the next release overwrites both, and `release-version.py check` fails on a manifest that disagrees. The release commit and tag are pushed over SSH with the deploy key in the `release` environment, so a ruleset on `main` can name that key as a bypass actor.
